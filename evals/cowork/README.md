# Cowork regression suite

A live [`cowork-harness`](https://github.com/yaniv-golan/cowork-harness) suite (CLI ≥ 3.10.0) that
protects the behaviours `SKILL.md` must keep when it is rewritten. It runs the skill the way
Claude Cowork does (`fidelity: hostloop`, plus six `fidelity: container` copies, see [Lanes](#lanes)), answers with a pinned model, and compares the same prompts
before and after the rewrite, one prompt at a time.

It is not a CI gate. Every run is a paid, live model call. Run it by hand before a release that
changes `SKILL.md`.

## Layout

| Path | What it is |
|---|---|
| `sessions/hostloop-sonnet5.yaml` | Setup shared by every scenario at both tiers (a session carries no tier; the name is historical): `claude-sonnet-5`, effort `medium`, the plugin at `../../../skill-package` declared under `remote_plugins` (staged as a UI-installed plugin is, see [Lanes](#lanes)), **no folders**. The agent's working folder is the harness's neutral outputs dir (`/var/empty` cwd at host-loop), never this repo, so the repo's `CLAUDE.md` cannot steer an answer. |
| `scenarios/t01…t20-*.yaml` | 20 **targeted** scenarios: 10 keep-list behaviours × 2 prompts, each built to trip one rule. Checked mechanically. |
| `scenarios/c01,c02,c07,c08,c19,c20-*.yaml` | **Container-tier copies** of the six targeted scenarios whose behaviour needs the skill's scripts to run (B1, B4, B10). Same prompt, session and assertions as the `t` original; only `fidelity: container` differs. Keep each pair in sync by hand. |
| `scenarios/g-pl-*.yaml` | 10 **general** scenarios, generated by `gen-general.js`. Checked by `semantic_matches` with a pinned judge. **Do not hand-edit.** |
| `claims/general-claims.json` | The generated rubric claims, with the generator model, prompt version and the sha256 of each source-lesson slice. |
| `gen-general.js` | Picks the general questions and generates their claims (`generate`), renders the scenarios (`write`), and checks whether the source lessons have changed since (`check`). |
| `run-suite.js` | Runs one arm and writes a manifest (`run`), compares two manifests per prompt (`compare`), and prints the post-hoc checks for one run dir (`derive`). |
| `results/` | Manifests, one JSON line per rep. Gitignored. Harness run dirs stay in `~/.cowork-harness/runs` (or `$COWORK_HARNESS_RUNS_DIR`). |

`sessions/` sits outside `scenarios/` on purpose: `cowork-harness run <dir>` and `lint <dir>` are
non-recursive and would report a session file as a scenario that fails to load.

## Where the skill's answer is

The skill runs `context: fork`. Its own answer comes back to the parent as a `Skill` tool_result that
starts `Skill "claude-code-internals" completed (forked execution).`, and the parent (Sonnet) then
rewrites it for the user. The `SKILL.md` rewrite changes what the fork does, so the targeted checks
read the **fork's return**. They use `tool_result_matches` / `tool_result_not_matches` anchored on
`completed \(forked execution\)`, which matches the Skill result and nothing else. Where the user-visible
relay matters too, a second `transcript_*` check reads it separately. Those relay checks are expected to
fail for reasons outside `SKILL.md`: Sonnet is known to drop `Read more` links when it relays.

`subagent_output_contains` does **not** see the fork's return. It reads only sub-agents the fork itself
dispatches (seen in the smoke: the fork dispatched a `general-purpose` agent).

## Lanes

The skill can be reached on three lanes, and the suite measures each one differently.

| Lane | Measured by | What it shows |
|---|---|---|
| **Local, host-loop** (Cowork on this computer) | `t01`–`t20`, `g-pl-*` at `fidelity: hostloop` | The local lane. The session declares the plugin under `remote_plugins`, so it is staged in the VM sidecar at `/sessions/<id>/mnt/.remote-plugins/plugin_<id>/`, the same place a UI-installed plugin sits in a live local-lane session (`scripts/state.js` at depth 8 under `/sessions`). As in production, `CLAUDE_SKILL_DIR` and `CLAUDE_PLUGIN_ROOT` are empty in the VM shell, and the `${CLAUDE_SKILL_DIR}` substituted into the skill body is a host path the shell cannot open. The scripts run only if the fork finds the staged copy itself; if it doesn't, it falls back to Read/Grep over `references/`. |
| **Script path** | `c01`, `c02`, `c07`, `c08`, `c19`, `c20` at `fidelity: container` | The same prompts, same session, with the agent itself inside the sandbox, so the `${CLAUDE_SKILL_DIR}` path in the skill body resolves in the shell and the scripts run without a search. B1 (`state.js` first), B4 (the `fetch-lesson.js` id trap) and B10 (`troubleshoot.js` / `xref.js` → `fetch-lesson.js`) run here as designed. |
| **Cloud** (where the maintainer's real sessions run) | By hand, one prompt, before and after | The harness cannot reproduce this lane, because every tier models the desktop-local lane. The cloud lane stages plugins under `/root/.claude/plugins/synced/<id>/…`, not `.remote-plugins`. In a real cloud session the model found the plugin there with `find` and ran `state.js` successfully. Check it by hand in a cloud Cowork session, once with the before `SKILL.md` and once with the after, using the `t01` prompt: *"Using the claude-code-internals skill: is /toggle-memory still a working slash command in the current Claude Code, and if not what replaced it?"* Record whether `state.js` ran and whether the answer named `/pause-memory`. |

A `c` scenario and its `t` original are not two samples of one measurement. Compare each one against
its own before arm, never against the other.

**Every container run fails its verdict. Read the assertions instead.** `SKILL.md` quotes a
`/Users/…` path, and some references do too. At `container`, the harness's `host_path_leak` guard scans
model-visible text, finds the quote, and fails the run. The guard has no waiver. Its only opt-out is
`transcript_no_host_path: true`, which runs the same scan and fails the same way. The guard is skipped
at `hostloop`. `compare` reads per-assertion results, not the verdict, so the before/after comparison
is unaffected. The manifest keeps the signal (`fail:host_path_leak`), so a change in it stays visible.

**Container needs a staged VM agent.** `hostloop` accepts a staged agent that is a patch newer than the
baseline pins (2.1.281 → 2.1.284). `container` does not. Point `COWORK_AGENT_BINARY` at the staged VM ELF
(`~/Library/Application Support/Claude/claude-code-vm/<ver>/claude`). Otherwise `run-suite.js` prints a
note and the `c` scenarios fail before they start. Use the same binary for both arms.

## Targeted behaviours (the keep-list)

Every targeted scenario also asserts `skill_triggered: claude-code-internals`, `tool_no_error: .*` and
`max_tool_errors: 0`, except the two offline scenarios, where a denied or failing shell call is the
point.

| # | Behaviour | Scenarios | Mechanical checks |
|---|---|---|---|
| B1 | State layer first | t01 `/toggle-memory`, t02 `/cost` (+ c01, c02) | `reference_read` of `state.js` or `references/state/`; the fork names the current answer (`pause-memory`, `/usage`). **Order** is derived by `run-suite.js` (`stateFirst`), because the harness has no ordering key. `stateFirst` is true when the fork touched the state layer before any search script, any lesson file or index, and any Grep/Glob over the whole `references/` directory. It is null when neither happened. |

| B3 | Lane qualification | t05 bash/env in Cowork, t06 plugin hooks in Cowork | The fork, and separately the relay, names the lane (host-loop / VM / cloud / remote / local). |
| B4 | id ≠ lesson number | t07 "Lesson 10 (Hooks)", t08 "Lesson 06 (Permissions)" (+ c07, c08) | A string found only in the right lesson body appears in a tool result (`fetch-lesson.js 10` returns the MCP lesson; `fetch-lesson.js 6` returns the Tool System lesson). The fork's answer carries a fact from the right lesson. |
| B5 | No-topic menu | t09 bare slash command, t10 "no topic" in prose | The menu lists several core subsystems (hooks, permissions, memory/compaction, MCP/plugins). No `fetch-lesson.js` access. `allow_stall`, because the menu ends on a question. t10 checks both the fork's return and the relay. t09 checks only the relay and asserts no `skill_triggered`, because a slash-expanded skill may not go through the Skill tool. That path is **unverified**. |
| B6 | Answer-size limit | t11 permissions end to end, t12 all of Cowork | The fork's return is under 5 KB plus its ~280-char wrapper, and the relay is under 7,000 chars. `toolResults` caps each result at 10 KB, which is above the 5,400-char threshold, so the check still fires on an oversized return. Asking which aspect matters (the >3-lessons rule) is also compliant, hence `allow_stall`. `run-suite.js` records the exact `forkChars` from `events.jsonl`. |
| B7 | `Read more` return contract | t13 undelivered file, t14 `rm` EPERM in outputs | The fork's return has `Read more: https://ccinternals.dev/cowork/…/?ref=skill`. No site link without `?ref=skill`, in the fork or in the relay. The relay keeping the link is recorded but not expected to pass. |
| B8 | Offline Read/Grep fallback | t15 shell denied by a scripted rule, t16 user says scripts can't run | `reference_read` of `references/` by Read/Grep. No Read/Grep errors. The fork's answer is right. |
| B9 | Runtime-observation caveat | t17 `/toggle-memory` "works for me", t18 `/background` "works for me" | The fork defers to or reconciles with the user's observation, or flags its own `2.1.231` baseline. |
| B10 | search → troubleshoot/xref → fetch | t19 a hook that won't fire, t20 hooks × permissions (+ c19, c20) | `reference_read` of the troubleshooting index (t19) or cross-references (t20), in script or JSON form, plus a lesson fetch. |

Cross-cutting checks: general CLI answers return no `ccinternals.dev` link; Cowork answers may return
one, but only with `?ref=skill`.

None of these read `SKILL.md`'s wording. They check behaviour, so they stay valid across the rewrite.

## General scenarios

- **Selection.** `gen-general.js` sorts the `plain`/`dev` questions in
  `../retrieval/questions-v2.json` by qid, shuffles them with `mulberry32(1)`, and takes the first 10.
  Nothing is hand-picked. Chosen qids and source lesson ids: pl-0274 (141), pl-0240 (123),
  pl-0116 (59), pl-0330 (168), pl-0166 (83), pl-0168 (84), pl-0420 (214), pl-0004 (3), pl-0390 (198),
  pl-0382 (193).
- **Claims.** For each question, `claude-fable-5-1` (not the answering model and not the judge) is shown
  the question and the exact lesson slice `fetch-lesson.js` returns. It writes 3–5 claims that a correct
  answer must make, and never a claim about tools, links or formatting (the judge cannot see tool
  calls). It runs as `claude -p --safe-mode --tools ""`, from a temp cwd. Claims are never hand-edited:
  to change them, bump `PROMPT_VERSION` and regenerate. `node gen-general.js check` fails if a source
  lesson changed after its claims were generated.
- **Judge.** `semantic_matches` with `judge_model: claude-opus-5-5` and `include_subagent_text: false`,
  so the judged document is the answer the user sees. The fork's own return is a tool_result, which
  the judge never receives. `min_pass` is a loose floor (half the claims). The real signal is the
  per-claim profile in `assertions[].semanticClaims`, which `compare` prints claim by claim.

## Running it

Auth: `--dotenv <path>` (or `$COWORK_DOTENV`) is passed through as the harness's **global** flag.

Before the first run of an arm: `git add -N` any new file under `skill-package/`, because the harness
stages git-tracked files only. Then commit the skill, so that the arm's `skillHash` names a recoverable
tree.

```bash
cowork-harness lint --min-severity WARN evals/cowork/scenarios/     # 7 WARNs expected, see below

export COWORK_AGENT_BINARY="$HOME/Library/Application Support/Claude/claude-code-vm/<ver>/claude"   # for the c scenarios

# BEFORE arm: current SKILL.md, 36 prompts (30 hostloop + 6 container) x 3 reps = 108 runs
node evals/cowork/run-suite.js run --arm before --reps 3 --dotenv <path>

# ABLATION arm, once: the 10 general prompts with every skill removed (--ablate-skill), x 3 = 30 runs
node evals/cowork/run-suite.js run --arm ablation --reps 3 --dotenv <path>

# ...the SKILL.md rewrite lands, commit it...

# AFTER arm: same prompts, same session, same COWORK_AGENT_BINARY, new SKILL.md (108 runs)
node evals/cowork/run-suite.js run --arm after --reps 3 --dotenv <path>

node evals/cowork/run-suite.js compare evals/cowork/results/before-*.jsonl evals/cowork/results/after-*.jsonl
cowork-harness stats --group-by skill-hash          # the harness's own view of the same runs
```

The manifest is `evals/cowork/results/<arm>-<UTC timestamp>.jsonl`. It gets one line per rep as the arm
runs, and its path is printed as `manifest: …` at the end. Each line carries the scenario's `fidelity`.

`--only t13,g-pl-0116` limits a run to scenarios whose names start with those prefixes.

### How results are compared

Comparisons are **per prompt**. For each scenario, `compare` prints each assertion's pass rate
before → after (by assertion index), each semantic claim's pass rate, and the medians of `stateFirst`,
`forkChars`, the fork's shell calls and cost. It flags any drop.

A rep only counts when all of these hold (the manifest's `invalidReasons` says which one failed):
- the skill was invoked, in every scenario that asserts `skill_triggered`;
- in the ablation arm: the result is stamped `ablated: true` and the skill was not invoked;
- `models` is exactly `claude-sonnet-5`;
- no model fallback happened.

`run` warns if one arm contains more than one `skillHash`. The harness's `run` has no `--label`, so the
generation is told apart by `skillHash` alone; `cowork-harness stats --group-by skill-hash` gives the
same split from the harness index.

With 3 reps a drop is a lead, not a verdict. Open both arms' run dirs (`cowork-harness trace <dir>`,
`verify-run <dir> <scenario>`) before calling it a regression. Assertions that are red in both arms, a
known gap, cannot regress. What matters is 3/3 → 0/3.

The ablation arm covers only the general prompts. With no skill, `skill_triggered` and every
fork-anchored check fail by construction. The per-claim profile is the one measure that shows whether
the skill adds anything over the model's priors. A claim that passes as often without the skill tests
the model, not the skill.

## Lint

`cowork-harness lint` reports 0 errors and 7 WARNs, all `prompt-slash-not-leading` (t01, t02, t16,
t17, t18, and the copies c01, c02). Those prompts mention a slash command in prose on purpose: the command is the subject of
the question, not an invocation.

## What this suite cannot measure

- **Script latency.** `toolDurations` includes model time.
- **Graded replay.** `semantic_matches` is live-only. Deterministic keys can be replayed from a
  cassette with `replay --strict`, but no cassettes are recorded here: the tier is host-inheriting, and
  `record` refuses a repo-visible path.
- **Full compaction coverage.** `compaction_occurred` sees only `compact_boundary`.
- **The remote (cloud) lane.** Every tier models the desktop-local lane. It is checked by hand (see [Lanes](#lanes)).
- **A passing verdict at `container`.** `host_path_leak` fails every run, because `SKILL.md` quotes a `/Users/…` path (see [Lanes](#lanes)).
- **Tool calls of a sub-agent the fork dispatches.** In the smoke, such an agent's reads were
  invisible (`toolsUsed: []`), so `reference_read` and `tool_result_contains` can miss evidence that
  exists.
- **The fork's return, for the judge.** `semantic_matches` sees the parent's relay, never the Skill
  tool_result.
- **Tool-call order.** No harness key checks it. `stateFirst` is derived post-hoc from `trace`.
- **Judge cost.** `cost.usd` covers the agent only. The judge call is not reported.

## Known behaviour (from the 2026-09-29 smokes)

### host-loop

- **The plugin is staged in the VM; the fork does not always find it.** `${CLAUDE_SKILL_DIR}` in the
  skill body is a host path, and `CLAUDE_SKILL_DIR` / `CLAUDE_PLUGIN_ROOT` are empty in the VM shell
  (`mcp__workspace__bash`), so `node ${CLAUDE_SKILL_DIR}/scripts/…` fails with `Cannot find module`.
  The staged copy is there all the same: under `remote_plugins` at
  `/sessions/<id>/mnt/.remote-plugins/plugin_<id>/skills/claude-code-internals/scripts/state.js`
  (depth 8 under `/sessions`), which is where a live local-lane Cowork session puts a UI-installed
  plugin. The first smokes declared the plugin under `local_plugins`, which stages it at depth 10
  (`mnt/.local-plugins/marketplaces/local-desktop-app-uploads/skill-package/…`). The fork's
  `find /sessions -maxdepth 8` stopped short of it and reported nothing, and the fork fell back to
  Grep/Read over `references/`. That was the fork's shallow search, not a missing mount. The partial
  results of that batch are kept, renamed `results/aborted-local_plugins-before-*.jsonl`.
- When the fork does try a script with the host path first, `tool_no_error: .*` /
  `max_tool_errors: 0` go red on that attempt. The `c` copies measure the script path without that
  step.
- t01 with `remote_plugins` (one run): the fork made no shell call. It ran five Grep calls over
  `references/state/` through the host-side file tools (host path of the staged copy), and all six
  assertions passed, with 0 tool errors. Cost $0.35, 29 s, model `claude-sonnet-5`. One run shows only
  that this path exists, not how often the fork takes it.
- Reading `references/state/registry.json` whole fails: it is 328 KB, and Read's limit is 256 KB.
- Sonnet dropped the fork's `Read more` links in the relay (t13), consistent with the earlier
  measurement.

### container (c01)

- With `remote_plugins` the plugin is staged at
  `/sessions/<id>/mnt/.remote-plugins/plugin_<id>/skills/claude-code-internals/`. The fork's first call
  was `node /sessions/<id>/mnt/.remote-plugins/plugin_<id>/skills/claude-code-internals/scripts/state.js toggle-memory`,
  and it succeeded. All six assertions passed, with 0 tool errors. Cost $0.27, 22 s. (The earlier
  `local_plugins` smoke staged it under `.local-plugins/…` and gave the same result, at $0.38.)
- The verdict failed on `host_path_leak` alone, triggered by a `/Users/…` quote from `SKILL.md`.
- Model `claude-sonnet-5`, staged agent 2.1.284 via `COWORK_AGENT_BINARY`.
