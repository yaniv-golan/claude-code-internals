# LESSON 254 — WHY IS MY MESSAGE REFUSED WITH ELEVATED_SESSION_UNTRUSTED_DEVICE?

**A cloud session can be marked `elevated`, which limits it to your trusted devices for good. It happens when the session is allowed to act on your computer. Writing into an elevated session needs a device proof: a trusted-device token plus a signature from the computer the session is bound to. A cloud session has no device, so a message from one to an elevated session is refused, and so is a message from a cloud session into a session on your own computer. `elevated_session_untrusted_device` is the session service's code for those refusals. No Claude Code build contains it, and retrying or signing in again doesn't change it.**

## Two things with similar names

- **Require trusted devices** is a setting, off by default. An Owner turns it on for a Team or Enterprise organization; on Pro, Max and Ultra you turn it on yourself. With it on, viewing or steering a Remote Control session needs an enrolled device and a recent sign-in. In the CLI it is the policy key `require_trusted_devices` behind the server flag `tengu_sessions_elevated_auth_enforcement` (default false).
- **An elevated session** is a property of one cloud session: `security_tier` is `elevated` instead of `standard`. It is not the setting. A session can be elevated while the setting is off.

## What makes a cloud session elevated (CODE-READ)

- **At creation.** A cloud session created with a device binding (`target_device_id` and a signed `bind_attestation` from this computer) can ask for `security_tier: "elevated"`. If the service doesn't accept this computer as a trusted device, the session is created `standard`, and the CLI warns that it is not limited to trusted devices.
- **Later.** In the CLI's route for running a cloud session's calls on your computer (`claude --cloud`, L202), a cloud session must be limited to your trusted devices, for good, before it can use a folder on your computer. The question has to be answered on a device that can prove itself: claude.ai on the web, the desktop app or the mobile app. A terminal that is not the bound computer can't answer it. Answering yes also marks everything attached to the session as trusted, so it can act on your computer with your authority. Whether Cowork's folder card (L215) elevates the same way was not traced. Users report that the question appears as a card asking to let the session use your computers and other sessions.
- **One way.** Nothing in the client turns an elevated session back to `standard`.

## Who can write into an elevated session (CODE-READ)

`SendMessage` to a `bridge:` address posts the message to `/v1/code/sessions/<id>/events` with your claude.ai OAuth token, plus:
- **`X-Trusted-Device-Token`**, if this computer holds one;
- **a device attestation** from `signForElevatedPeer`. The CLI first reads the target session. If its tier is `elevated`, it signs the message with this computer's device key, but only if the session is bound to this computer. A session bound to another device gets no signature (`bound_elsewhere`).

Signing is skipped when there is no stored token and in any cloud session (`CLAUDE_CODE_REMOTE`). The token comes from enrollment: a request to `/api/auth/trusted_devices` after a claude.ai sign-in, which also sends you an email. `CLAUDE_TRUSTED_DEVICE_TOKEN` takes precedence over enrollment. Enrollment is skipped without OAuth, under essential-traffic-only, and when the organization hasn't turned trusted devices on. So with the setting off, a terminal may hold no token and can't sign, even on the computer the session is bound to (inferred; it matches a report in #103864).

**On a 403 with `resource: untrusted_device`:** the CLI reads `sub_reason`. With none, `bound_unattested` or an unknown value, the token was refused. It then enrolls once and retries: at most every 5 minutes, and not again within 24 hours of an enrollment made after a refusal. `served_call_unsigned` means a signature was wanted, and it doesn't re-enroll.

## The two send paths

- **From a session on your computer:** the CLI path above. Its refusals read as "this computer is not a trusted device for your account yet" or similar, and never carry the `elevated_session_untrusted_device` code.
- **From a cloud session:** the CLI's own post is refused. Its credential covers the session's own work, not delivery to another session (401), or the target wants a device proof (403). The CLI then points the model at the session service's own tool: `send_message` on the `claude-code-remote` MCP server (`/v2/ccr-sessions/-/meta/mcp`). That server tool returns the service's codes, `elevated_session_untrusted_device` among them, and its refusals are non-retryable.
- **Checked before sending:** in a cloud session with no `CLAUDE_TRUSTED_DEVICE_TOKEN`, whose organization enforces trusted devices, `isRemoteControlPeerUnreachableFromHere` is true. `ListAgents` then marks Remote Control sessions unreachable from here, and `SendMessage` and `SendFile` refuse them up front (`unreachable_elevated`), saying nothing was sent.

## What the service refuses (REPORTED)

From several accounts in #103864, with "Require trusted devices" on and off:

| From | To | Result |
|---|---|---|
| Session on your computer | Standard cloud session | Delivered |
| Session on your computer | Elevated cloud session | 403, "elevated session requires a trusted device", even after a fresh `/login` |
| Standard cloud session | Standard cloud session | Delivered both ways |
| Standard cloud session | Elevated cloud session | `elevated_session_untrusted_device` |
| Standard cloud session | Session on your computer | `elevated_session_untrusted_device`: only a session allowed to reach your other sessions may do this |
| Elevated cloud session | Session on your computer | Delivered, but each send may ask "Allow Claude to Send Message?" |
| Elevated cloud session | Other cloud sessions | Refused |

- **When it began:** setups that worked until about 18 October 2026 were refused from about 20 October, with no client update in between, so the change was server-side.
- **Approving on a phone doesn't help.** Neither approving a call nor marking the parent session trusted lets a child cloud session reply to it.
- **Projects:** with the setting on, a Project can't start or stop sessions on your computer at all.

## What to do

- **An orchestrator with cloud workers:** keep the orchestrator `standard` (decline the folder/computer question) so workers can reply. Or have workers report through something the orchestrator already reads, such as a pushed branch, a PR comment or an issue, or have the orchestrator check them with `get_session` or `list_events`.
- **The orchestrator must act on your computer:** run it there, in a local session with Remote Control. Local sessions reach standard cloud workers, and a Remote Control session that a Project started itself talks to the Project both ways (REPORTED).
- **Reading the refusal:** this code means the sender's kind or tier, not the message. Retrying, rewording or `/login` won't change it. Re-enrolling (`/login`) only helps with the CLI-path messages about this computer's token.
- **Asking for a change:** #103864 asks for a reply-only grant and a per-session allow; it is open.
