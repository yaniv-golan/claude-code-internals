# LESSON 253 — CAN I USE ARTIFACTS FROM THE AGENT SDK OR A HEADLESS RUN, AND HOW DO COMMENTS REACH ME?

**The `Artifact` tool works in an Agent SDK or `claude -p` run only when the session is signed in with a claude.ai OAuth token carrying the `user:inference` scope and `CLAUDE_CODE_ARTIFACT=1` is set. An API key never gets it. Everything is published to the claude.ai account behind that token. Comments come back to a session in two ways: a live connection while the session runs, or, for a cloud session, a webhook trigger that only Anthropic's hosted service can create. Your own server cannot subscribe; it can only poll.**

## When the tool is offered

The CLI decides in three steps. Each step has a reason code, which telemetry records as `withheld_reason`.

**1. Is the session signed in the right way?** The tool needs either:
- claude.ai OAuth that is the active credential, with `user:inference` among the token's scopes; or
- the OIDC federation env quad (L86).

With `ANTHROPIC_API_KEY` or `apiKeyHelper` as the credential source, the OAuth check is false, so the tool is never offered. `CLAUDE_CODE_OAUTH_TOKEN` counts as OAuth. Its scopes come from `CLAUDE_CODE_OAUTH_SCOPES`, and without that variable they default to `user:inference` alone, which is enough.

**2. Is this kind of session allowed?** These reasons are checked in order:

| reason | when |
|---|---|
| `surface_excluded` | `CLAUDE_CODE_ENTRYPOINT` is `local-agent` or starts with `claude-coworker`. Cowork has its own artifact tools (L212). The one exception is a `local-agent` session that Desktop has marked for frame artifacts. |
| `third_party_provider` | the provider is not first-party (Bedrock, Vertex, Foundry) |
| `essential_traffic_only` | non-essential traffic is disabled |
| `artifact_env_off` | `CLAUDE_CODE_ARTIFACT` is set to a false value |
| `sdk_default_off` | the entrypoint is `sdk-ts`, `sdk-py`, `sdk-cli`, `claude-code-github-action` or `mcp`, **and** neither `CLAUDE_CODE_ARTIFACT` nor `CLAUDE_CODE_BRIDGE_CHILD_ARTIFACT` is set to a true value |

So in the Agent SDK the tool is **off unless you opt in** with `CLAUDE_CODE_ARTIFACT=1`. A plain `claude -p` run is also off by default: at boot, a non-interactive session with no entrypoint set is stamped `sdk-cli`. `mcp` is `claude mcp serve`. Only an interactive session gets the tool without opting in.

**3. Do the switch, the server flag and the org allow it?**
- **The switch.** `enableArtifact` is a setting from 2.1.322; it was not in 2.1.319. It replaces `disableArtifact`, which is still honoured when it's `true`. It defaults to on. Off in managed settings, `--settings` or user settings wins. Project and local settings can only turn it off. `CLAUDE_CODE_DISABLE_ARTIFACT` also turns it off. `/config` shows it as "Artifacts".
- **The server flag.** `tengu_cobalt_plinth` is a server flag. When the server sends no value, it defaults to on for:
  - Team and Enterprise accounts;
  - a consumer OAuth account;
  - no claude.ai sign-in at all.

  Step 1 still has to pass, so the default doesn't matter for an API-key session.
- **The org setting.** The account's plan must be Team, Enterprise, Pro or Max (or unknown), and the org setting `allow_cobalt_plinth` must allow it. For OIDC federation on a Pro or Max plan, the org setting has to be readable. Otherwise the tool is withheld, with reasons such as `org_policy_unverifiable`.

## Where a publish goes

A local or container session publishes **straight to the main Anthropic API host**, to paths under `/api/frame/`:
- `deploy/prepare` and `deploy/direct`;
- `upload`, `comments/…`, `db/…`, `blob/…`;
- `watch-token/<slug>` and `subscribe/<slug>`.

The request carries the claude.ai OAuth access token as a bearer token. The artifact belongs to that token's account, and the shared-with list is managed on claude.ai.

**Trap:** `CLAUDE_CODE_ARTIFACTS_API_BASE_URL` and `CLAUDE_CODE_ARTIFACTS_API_TOKEN` do nothing in the shipped CLI. The frame host's override function returns `undefined` unconditionally. As a result:
- the base URL is always `BASE_API_URL`;
- the code that would send `CLAUDE_CODE_ARTIFACTS_API_TOKEN` as the bearer never runs;
- a separate artifacts token can't stand in for an OAuth sign-in.

Both variables are still on the env-strip lists (L172).

Cloud sessions (`CLAUDE_CODE_REMOTE`) have a second route. Publishes and comment calls can go through the session gateway as a relay, behind `tengu_cobalt_plinth_sorrel`; in that route the direct call is refused. That route never applies to a process you run yourself.

## How comments come back

There are two mechanisms, and neither one delivers to your own server.

- **Live, while the session runs.** The CLI holds a subscription token for each artifact it watches. The token's transport is `live` or `sync`, and the CLI renews it with `POST /api/frame/watch-token/<slug>`. Comments arrive in the running session as they're posted. When the process exits, nothing is listening. In a per-turn container, that means no comment wakes anything.
- **Durable, for cloud sessions.** It works in four steps:
  1. The CLI calls the `watch_url` tool on the claude.ai gateway MCP connector.
  2. That tool creates a webhook trigger and returns `url`, `trigger_id` and a `sealed_secret`.
  3. The CLI only accepts a URL of the form `https://…/integrations/v1/code/webhook-triggers/<id>/fire`.
  4. It sends `POST /api/frame/subscribe/<slug>` with that URL, the secret and `events: ["published","comment"]`.

  A comment then fires the trigger, which starts or wakes the cloud session. The CLI won't accept any other URL, so your own server can't be the target.
  - **Failure reasons:** `session_not_found`, `session_device_bound`, `org_not_enabled`, `tool_not_offered`, `url_webhook_trigger_limit`, `no_originator`, `subscribe_forbidden`, `relay_unavailable`.
  - **Trigger cleanup:** a trigger that fails to release counts against the session until the session ends.

**What a host process can do:** read a thread with `GET /api/frame/comments/<slug>`, with the same OAuth bearer. Add `?names=1` to get author names. This is an internal API with no compatibility promise, so poll it carefully. Comment authors are human, agent or unknown (L156).

## Traps for anyone building on this

- **The owner is the token's account.** Every artifact belongs to whichever claude.ai account owns the OAuth token. In a multi-user bot, they all belong to the bot's account, not to the people chatting with it.
- **Viewers need claude.ai.** Whoever opens or comments on an artifact must be signed in and have access, unless it is shared publicly.
- **The viewer pays for "ask Claude".** A page that uses the `sample` capability bills the person viewing it, not the account that published it.
- **Scripts load only from five CDNs.** The tool's instructions allow cdnjs, jsdelivr (npm), unpkg, cdn.tailwindcss.com and code.jquery.com, and tell the model to inline everything else. A page that needs a script from another host, such as a messaging app's webview SDK, is outside that list. The CSP the served page actually enforces is set server-side and wasn't read here.
- **Reading the opt-out.** When the tool is missing, check the reason in this order: the credential source, then the entrypoint, then `CLAUDE_CODE_ARTIFACT`. `/config` alone can't explain it, because the toggle only reflects the switch in step 3.
